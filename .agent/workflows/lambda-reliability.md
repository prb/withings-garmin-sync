# Lambda Reliability and Availability Rules

Apply these rules to Lambda handlers, their external calls (LLM, NPS, weather, S3, SSM, DynamoDB), and any change that affects what production stores or shows. They exist because a collector bug once hid 38% of snapshots for months (see DESIGN.md) and because swallowed failures are invisible by construction. For changes to models, prompts or decision questions, and the evidence needed before promoting a new model path, see model-change-guidelines.

- **Never report success after dropping work.** A handler that cannot finish a record must retry it, write a durable failure record, or send it to a dead-letter queue. Returning a normal response that only mentions the error in its body, or logging and continuing, is not handling.
- **Bound every external call.** Each call has a timeout and an overall deadline shorter than its Lambda's timeout. The retry budget (attempts x timeout + backoff) must fit inside that deadline, honor `Retry-After`, and retry timeouts as well as connection errors. Do the cheap, essential write (for example the raw snapshot) before the slow call, not after it.
- **Fallbacks must be reachable, visible, and explicitly tested.** A fallback path needs a test that forces the primary to fail, must be reachable before the Lambda can be killed, and must record that it ran in logs and in the stored item (a flag plus the identifier of what produced the value). Never present fallback output as primary output.
- **Failure paths get an alarm and a test.** Every new way a handler can fail gets a metric or alarm (for example messages sent to a dead-letter queue, extraction errors, fallback rate, sustained 429s) and an offline test that triggers it.
- **Validate model output before storing it.** Check the answer's type, keys and choice membership against the options that were offered, and fail into the explicit fallback path on a mismatch. Store the served model version and provider from the response, not only the configured alias.
- **Launch new behavior dark.** A new path that changes what production stores or shows (a new model, prompt, prediction method, provider or rewritten pipeline step) ships behind a feature flag or in shadow mode first. Declare every switch in infrastructure (the CDK function environment) with the incumbent as the default, so promotion and rollback are reviewable configuration changes rather than code defaults or console edits. In shadow mode, write the incumbent's result first and the new path's result to separate attributes or items; a shadow failure must not affect the incumbent and must itself be recorded. Do not remove the incumbent path in the same change; keep it until the new path has operational history.
- **No implicit bulk reprocessing.** A deploy must not trigger reprocessing of history. Run it deliberately: rate-limited, deduplicated by distinct input, resumable, with failures counted across batches, and published only after a complete run.
- **One logical change per PR.** Do not combine independent concerns (for example extraction, identification, images and prediction) in one change.
